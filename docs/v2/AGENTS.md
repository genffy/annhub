# v2 产品文档约定

> 仅适用于 `docs/v2/`。这里保存目前已确认、仍会迭代的产品结论，不规定最终 monorepo 包结构。
> 更新：2026-10-10。

## 内容边界

- 本目录是产品设计真源：写行为、契约和验收，不写实现位置。不引用代码文件、模块名、消息名或测试数量。
- 从 [README.md](README.md) 的文档地图找到唯一归属文件，再修改对应结论；其他文档用摘要和链接，不复制整套规则。
- 只保留最终确认的内容和扁平导航，不另建过程性 CHANGELOG；未确认的技术选型不要写成既定工程结构。
- **只写目标，不写演变**：不写“已移出”“取代”“原来”“不再”“旧实现”，不解释缺号，不保留已采纳决策的记录；一个能力不在范围内，就在不做清单里用现在时说明边界，不交代它曾经存在。历史看 git。
- **未确认的想法、阈值和方案只写进 [validation.md](validation.md)**。其他文件需要引用时，只写条目 ID（如“见 Q-17”）。

## 从想法到真源

1. 新想法先登记为假设（`H-`）或待确认决策（`D-`），写明通过判据、验证方式和不通过时的动作。
2. 实验产出证据；证据和产品负责人的确认齐备后，把结论迁入归属文件。
3. 把结论迁入归属文件，并把原条目从 validation.md 删除；不另建变更记录，也不保留“已决”表，原因与演变看 git。
4. 被采纳的新能力同时补齐：[user-stories.md](user-stories.md) 的故事与验收、[metrics.md](metrics.md) 的指标或事件、[roadmap.md](roadmap.md) 的范围条目。

## 状态怎么写

| 维度                             | 唯一入口                              |
| -------------------------------- | ------------------------------------- |
| 交付状态：这个范围做完了吗       | [roadmap.md](roadmap.md)              |
| 验证状态：真实用户用了吗、有效吗 | [validation.md](validation.md) 的假设 |

目标契约与当前实现分开写：规格文档只写目标契约，实现状态只写在 roadmap.md。声称“已实现”前核对源码或测试。

## 编号

| 前缀               | 含义                   |
| ------------------ | ---------------------- |
| `US-`              | 用户故事               |
| `M-`               | 指标                   |
| `H-` / `E-` / `D-` | 假设 / 实验 / 决策     |
| `RK-` / `Q-`       | 风险 / 开放问题        |
| `AP-`              | 官网的 AI 搜索探针提示 |

编号稳定，不复用，不因排序改变；缺号不需要解释。

## 写作规范

- 使用相对链接；移动文件后检查引用。日期写实际修改日期，图片资源放对应模块的 `assets/`。
- 条目类型的必填字段与预设属性只在 [entry.md](entry.md) 写一次；新增类型或内置属性按它的 §8 清单。
- 示例使用中性来源（如 `engineering.example.com`），不使用真实用户数据；涉及人物时用角色或代号。
- 外部事实（价格、功能、政策）只写在 [market.md](market.md)，带来源链接和核对日期，超过 90 天重新核对。对外页面引用这些事实时同样带日期。
- 新增功能规格前，用 [validation.md §8](validation.md) 的模板自检。
- 设计稿在 [docs/design/v2](../design/v2/README.md)：界面文案和规则先改本目录，再同步设计稿，不在设计稿里另写一套。
