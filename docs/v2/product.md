# 产品定位

> 层级：vision
> 状态：产品定位真源
> 更新：2026-10-07

本文定义 AnnHub 为谁服务、解决什么问题、为什么不是另一个笔记软件，以及从现有产品中借鉴和拒绝什么。

## 1. 一句话定位

**AnnHub 是一个本地优先的浏览器扩展：从网页或自己的灵感中，把值得留下的文字、图片和问题连同语境保存下来，再通过理解、核验、应用，让它成为可调用的个人知识；需要时可检索、回看或导出。**

对外短句：

> 不是帮你收藏更多，而是让真正值得收藏的内容至少经历一次理解，并写明准备用在哪里。

## 2. 目标用户

### 2.1 核心用户

首版只为以下三类重度知识工作者优化：

| 用户                | 高频材料                           | 日常产出                                  |
| ------------------- | ---------------------------------- | ----------------------------------------- |
| 软件工程师 / 架构师 | 技术文档、源码说明、RFC、事故复盘  | 设计文档、技术方案、Code Review、故障分析 |
| 产品经理 / 设计师   | 行业文章、竞品、研究报告、设计案例 | PRD、决策记录、方案比较、设计说明         |
| 研究者 / 分析师     | 论文、报告、新闻、数据解释         | 分析文章、研究笔记、观点论证、结论汇报    |

共同特征：

- 每周阅读大量网页材料。
- 已经使用过笔记、书签、高亮或稍后读工具。
- 真正的问题不是无法保存，而是保存后无法在工作中调用。
- 主要工作设备是桌面浏览器。
- 愿意为高价值内容多花 30 到 90 秒完成一次加工。

原创灵感和短随感也是 Fragment：用户自己写下内容与触发背景，不伪装成网页摘录；长篇文章不属于 AnnHub，留在用户自己的写作工具里。

#### 代表画像（待验证的假设）

下表是待校正的假设画像，不是调研结论；招募条件与校正方式见 [validation.md §2](validation.md)。

| 画像               | 典型一周                                  | 触发采集的时刻                           | 现有替代                     | 失败的代价                                       |
| ------------------ | ----------------------------------------- | ---------------------------------------- | ---------------------------- | ------------------------------------------------ |
| P1 工程师 / 架构师 | 读文档、RFC、复盘；评审或撰写一两份方案   | 遇到新概念、约束或故障模式               | 书签加笔记工具，偶尔手工制卡 | 写方案时重新搜索同一批资料；评审时说不清取舍理由 |
| P2 产品 / 设计     | 读行业文章、竞品、用户研究；写 PRD 或比较 | 看到与当前方案相关的论点、案例或界面细节 | 截图加文档链接               | 方案缺证据；记不清某个设计为何有效               |
| P3 研究者 / 分析师 | 读论文、报告、新闻；整理论证              | 遇到相互冲突的主张或关键数据             | 文献管理器加笔记             | 引用时丢失前提；把作者观点当成事实               |

P3 的主要来源可能是 PDF，网页是否足够见 [H-15](validation.md)。

### 2.2 暂不优化的人群

- 只想一键收藏、以后搜索的人。
- 需要团队 Wiki、实时协作和权限管理的组织。
- 以应试背题为主要目标的用户。
- 以手机为主要采集和学习设备的用户。
- 需要完整学术引用格式和文献管理的人。
- 为社交平台制作配图的内容创作者。因此 R5.1 美化与品牌、R5.2 导出增强后置，以 [H-14](validation.md) 为入口门槛（[D-02](validation.md) 已采纳）。

### 2.3 明确不做的事

| 不做                             | 原因                                             | 详见                                |
| -------------------------------- | ------------------------------------------------ | ----------------------------------- |
| 团队 Wiki、实时协作、权限管理    | 单人本地优先是核心验证；协作引入账号、权限与冲突 | —                                   |
| 手机端                           | 先把桌面浏览与深度工作的闭环验证清楚             | §2.2                                |
| 桌面客户端与间隔复习             | 产品收窄为浏览器扩展：采集、加工、检索、导出     | [D-17](validation.md)               |
| 通用笔记与自由白板               | 避免成为另一个笔记软件                           | §4                                  |
| 稍后读收件箱与完整阅读器         | 保存意图必须在采集现场分流                       | §5.2                                |
| 输出工坊与知识关系（含全库图谱） | 经 UI/UX 设计走查判断不适合落地                  | [D-10](validation.md)               |
| AI 代写“应用”                    | 用户先生成；建议不等于事实                       | §5.3                                |
| 通用聊天窗口                     | AI 只做摘要提取与核验建议，不开放对话入口        | [ai.md §1](ai.md)                   |
| 平台发布与账号授权               | 真实发布动作不进入扩展域                         | [screenshot.md §1.1](screenshot.md) |

## 3. 核心 Jobs-to-be-Done

### Job A：浏览时固化理解

> 当我在网页中遇到一个重要概念、论点或方法时，我希望快速保留原文和语境，并写下它为什么重要，以免之后只剩一段无法理解的摘录。

### Job B：写作或决策前找回知识

> 当我准备写方案、做比较或解释问题时，我希望看到与当前主题有关、我曾经加工过的碎片，而不是重新搜索整篇文章。

| Job                    | 触发时刻                     | 现有替代               | 失败的代价                 | 成功信号                                     | 层与指标                                    |
| ---------------------- | ---------------------------- | ---------------------- | -------------------------- | -------------------------------------------- | ------------------------------------------- |
| A 浏览时固化理解       | 遇到重要概念、论点或方法     | 高亮、书签、复制进笔记 | 之后只剩一段无法理解的摘录 | 脱离原网页仍可独立理解（质量抽样）           | L1–L2；M-02、M-05                           |
| B 写作或决策前找回知识 | 开始写方案、做比较、解释问题 | 重新搜索、翻笔记       | 重复检索同一批资料         | 搜到的碎片带着当时的理解与应用，不必再读原文 | 检索（[search.md](search.md)）；阶段 V 访谈 |

## 5. 核心差异化

### 5.1 Fragment 不是 Note，也不是 Highlight

AnnHub 的核心对象是一个可应用的 Fragment：

```text
内容
+ 原始语境
+ 来源与定位
+ 用户的理解
+ 核验确认或修正
+ 应用承诺
```

高亮可以很多，Fragment 应该少而有价值。

### 5.2 两条明确分流

浏览器中所有保存动作必须先回答一个问题：

```text
只是以后查阅？ -> Highlight / Clip
准备理解并使用？ -> Fragment
```

AnnHub 不通过降低 Fragment 标准来追求采集量。用户不想加工时，应当安全退回高亮，而不是生成半成品 Fragment。

### 5.3 AI 建议与用户事实分离

- AI 可以建议摘要和核验。
- 用户必须确认会改变知识状态的结果。
- 用户写下的理解和应用不能由 AI 代写。

### 5.4 本地优先但不封闭

- 断网时仍可采集、查询和编辑。
- 已提交内容和图片可导出为 Markdown ZIP，供其他工具阅读。
- ZIP 供其他工具阅读，不作为 AnnHub 数据库的恢复格式。

### 5.5 核心赌注与证伪信号

AnnHub 押注下面三件事。每一件都写明“如果错了会看到什么”，验证方式见 [validation.md](validation.md)。

| 赌注                     | 具体表述                                                               | 支持证据                                                                      | 证伪信号                                                                | 退路                                     |
| ------------------------ | ---------------------------------------------------------------------- | ----------------------------------------------------------------------------- | ----------------------------------------------------------------------- | ---------------------------------------- |
| B1 加工门槛换价值密度    | 用户愿意在采集现场多花 30–90 秒，换取日后可调用的知识；Fragment 少而精 | 精细询问与自我解释被评为中等效用（[learning-model.md §6](learning-model.md)） | 打开采集窗口后保存率低，多数人退出（[H-01](validation.md)）             | 保留 Highlight/Clip 安全出口；削减必填项 |
| B3 本地优先建立信任      | 数据留在本地并可开放导出，降低迁入顾虑                                 | Omnivore、Pocket 的关停（[market.md §4.1](market.md)）                        | 用户更在意手机与云同步，压过本地信任（阶段 V 访谈）                     | 评估同步与移动端                         |
| B4 AI 在用户生成之后辅助 | 先写后看；AI 建议须经确认                                              | AI 先给答案会损害后续独立表现（Bastani 等，2025）                             | 用户普遍要求 AI 代写应用，且认为这没有损害理解（[H-11](validation.md)） | 增加受控的 AI 起草，仍须用户确认         |

### 5.6 价值时间线

用户在不同时刻应当得到什么，以及目前哪里有空白。空白是待验证的风险，不是已确认的缺陷。

| 时刻      | 用户得到什么                                             | 靠什么实现             | 空白                                                |
| --------- | -------------------------------------------------------- | ---------------------- | --------------------------------------------------- |
| 第 1 分钟 | 选区被留住，带来源与语境，没有被表单拖住                 | 三种保存层级、快速剪藏 | 首次见到采集窗口的理解成本（[H-05](validation.md)） |
| 当天      | 第一条加工过的碎片：写下了自己的理解和准备怎么用         | 采集窗口、碎片库       | 加工带来的价值要多久才能被感受到                    |
| 第 1 周   | 数条自己的碎片；写方案时能搜到当时的理解与应用，不必重读 | 碎片库检索、回到来源   | 找回是否真的发生（阶段 V 访谈）                     |

## 6. 产品原则

1. **价值密度高于采集数量**：默认不展示“今日收藏多少条”作为成就。
2. **原文永远可追溯**：所有自动摘要必须能回到来源语境。
3. **用户先生成，系统后辅助**：理解步骤先于模型答案。
4. **失败不丢思考**：网络、模型和保存失败都保留用户输入。
5. **建议不等于事实**：自动推断和模型建议必须可识别、可拒绝。
6. **默认界面克制**：主流程不要求用户理解数据库或存储细节。

## 7. 产品护城河假设

AnnHub 的壁垒不在剪藏或高亮中的任何单项，而在长期积累的加工数据：

- 用户在哪类语境中采集什么知识。
- 初次理解与核验后的差异。

这些数据可以逐步改善各 kind 的采集提问，但本地存储永远是离线真源。

## 8. 主要风险与应对

完整风险登记（可能性、影响、预警信号）见 [validation.md §6](validation.md)；下表只保留产品层面的应对。

| 风险             | 表现                  | 产品应对                                                          |
| ---------------- | --------------------- | ----------------------------------------------------------------- |
| 采集摩擦过高     | 用户看到 Modal 就退出 | 保留 Highlight/Clip 快速出口；Fragment 表单按 kind 只显示必要字段 |
| 结构化数据不透明 | 用户担心被产品锁定    | R1 Markdown + 原图 ZIP，以及清楚说明的导出范围和缺失项            |

## 9. 成功定义

AnnHub 成功不是用户存了很多内容，而是形成以下重复行为：

```text
每周捕获少量高价值 Fragment
  -> 写方案或做决策时搜到并用上
  -> 回到来源修正理解
```

对应用户故事见 [用户故事与验收](user-stories.md)，指标定义见 [体验与指标](metrics.md)。这些行为是否真的出现，由 [validation.md](validation.md) 的阶段 V 回答。
