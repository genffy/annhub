# 验证计划与决策登记

> 层级：product
> 状态：持续维护；本目录中唯一存放**未确认内容**的文件
> 更新：2026-10-10

本文回答三个问题：**哪些判断还没有证据**（假设）、**打算怎样验证**（实验）、**哪些决定在等待产品负责人确认**（决策）。已确认的结论只写在各自的真源文件里；本文的条目被采纳后迁入真源，并从本文删除。

## 1. 规则

1. 未确认的想法、阈值和方案只在本文登记，不写进其他真源文件。其他文件需要引用时，只写条目 ID（如“见 Q-17”）。
2. 每个条目有稳定 ID：假设 `H-`、实验 `E-`、决策 `D-`、风险 `RK-`、开放问题 `Q-`。ID 不复用，不因排序变化。
3. 状态词：假设为 `待验证` → `验证中` → `通过` / `未通过`；决策在第 5 节登记，确认后把结论写进归属文件，并从本文删除该条目。
4. **阈值是方向性判据，不是统计结论**。内测人数在个位数到几十人之间，结论用来决定“继续、修订还是停止”，不用来宣称显著性。所有比例必须同时报告分母。
5. 晋升流程：假设 → 实验 → 证据 → 决策 → 产品负责人确认 → 迁入归属文件。证据不足时不得跳步。
6. 评审节奏：内测期间每周一次指标回顾（30 分钟），每两周一次决策评审；外部事实类文档（[market.md](market.md)）每 90 天复核。

每条待确认的决策给出选项、推荐和“无回复时的默认”。产品负责人确认后，结论写进归属文件，并从本文删除该条目。

### D-22 采集用时的口径与分桶

背景：M-03 要求“从触发到保存成功”的中位和 95 分位，并设了“剪藏的本地写入 95 分位 < 300ms”的护栏；但 `capture.saved` 的 `duration` 只有 < 15 秒、15–30 秒这样的粗档，300ms 落在最小一档里，事件算不出这个目标。事件在条目写入成功时记录，触发点却在页面里（用户的点击），两者之间还隔着一次消息往返。

| 选项 | 内容                                                                                                                                                        |
| ---- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A    | `capture.saved` 的 `duration` 单独使用细档：< 150ms、150–300ms、300–600ms、0.6–1.5 秒、1.5–5 秒、≥ 5 秒，口径取“用户点击到写入成功”；通用分桶仍用于其他事件 |
| B    | 保持通用分桶，把 M-03 的护栏改写成粗粒度（如“95% 的剪藏在 15 秒内完成”），毫秒级目标只由自动化性能测试守                                                    |
| C    | 在 A 之外，本机再按天记录中位与 95 分位的数值（仍是聚合数字，不含内容）                                                                                     |

推荐：A。阶段 V 要用本地指标回答“够不够快”，细档仍是分桶数字，不泄露内容；C 多一层存储，有需要再加。
无回复时的默认：A。
影响的文档：[metrics.md](metrics.md) 第 5 节（M-03）与第 9 节（耗时分桶的通用规则加一条例外）、[extension.md 第 8 节](extension.md)。

### D-23 导出里剪藏正文是否带“原文”章节标题

背景：[storage.md 第 6 节](storage.md)的正文说明把“原文”列为剪藏的第一个章节，示例却在 frontmatter 之后直接写原文、没有“原文”标题，后面才是“高亮备注”“备注”。原文自己带二级标题时，再加一个“原文”标题，会让网页的标题与 AnnHub 加的章节标题同级，读者分不清。

| 选项 | 内容                                                                   |
| ---- | ---------------------------------------------------------------------- |
| A    | 原文不加标题，其余章节（语境、高亮备注、备注）用二级标题（示例的写法） |
| B    | 原文加“原文”二级标题，并把原文里的标题整体下移一级                     |
| C    | 原文加“原文”二级标题，不动原文的标题级别                               |

推荐：A。与示例一致，导出的笔记读起来就是原网页的内容，AnnHub 加的章节在后面；章节标题是固定的本地化短语，原文里恰好出现同名标题的概率可以忽略。
无回复时的默认：A。
影响的文档：[storage.md](storage.md) 第 6 节的正文说明。

### D-24 高亮视图里分组的次序是否随搜索变化

背景：[search.md 第 5 节](search.md)规定“组按组内最新高亮的创建时间降序……无搜索词与有搜索词时的分组顺序一致，搜索只决定哪些高亮留下”。“组内最新高亮”可以读作该剪藏的全部高亮，也可以读作搜索后留下的高亮，两种读法在搜索时给出不同的组序。

| 选项 | 内容                                                   |
| ---- | ------------------------------------------------------ |
| A    | 按该剪藏全部高亮里最新的一条排序，搜索与筛选不改变组序 |
| B    | 按搜索与筛选后留下的高亮里最新的一条排序               |

推荐：A。与“顺序一致”这句明确的话一致，加上搜索词只会看到组变少，组序不跳。
无回复时的默认：A。
影响的文档：[search.md](search.md) 第 5 节补一句“最新高亮取该剪藏的全部高亮”。

### D-25 shadow root 与同源 iframe 里的选区，以及最低浏览器版本

背景：[capture.md 第 3 节](capture.md)保证同源 iframe 与 open shadow root 里的选区和区块可用，跨源 iframe 不出现入口。shadow root 里的选区，只有标准接口 `Selection.getComposedRanges` 才给得出真实范围（预计 Chrome 137 起提供，以实测为准），而最低支持版本是 114（[permissions.md 第 5 节](permissions.md)）。同源 iframe 要求页面脚本在子框架里运行，写入类消息的发送者校验也要认得同源的子框架。

| 选项 | 内容                                                                                                                            |
| ---- | ------------------------------------------------------------------------------------------------------------------------------- |
| A    | 最低版本提高到能用 `getComposedRanges` 的版本，shadow 内的选区直接用它                                                          |
| B    | 最低版本不变：有 `getComposedRanges` 时用它；没有时降级，用 `Selection.toString()` 做纯文本剪藏（无行内格式、无语境），仍然保存 |
| C    | 缩小保证范围：shadow root 与 iframe 里只保证区块入口，选区剪藏不保证（改 capture.md 第 3 节与 extension.md 第 8 节）            |

同源 iframe 对三个选项一致：页面脚本在所有框架注册；子框架里只有与顶层同源时才启用入口，跨源时静默不工作；后台只接受“与该标签页顶层同源”的子框架发来的写入，消息带框架标识。

推荐：B。不动清单与权限说明，新版本上得到完整行为，旧版本上仍可用。
无回复时的默认：B。
影响的文档：[capture.md](capture.md) 第 3 节；选 A 时还有 [permissions.md](permissions.md) 第 5 节、清单与隐私政策里的最低版本。

### D-26 `datetime` 属性值是否必须是真实存在的日期时间

背景：[entry.md 第 5.2 节](entry.md)规定 `date` 必须是真实存在的日期，`datetime` 只写“与 Obsidian 的日期和时间格式一致”，没有说明不合法的取值（如 `2026-02-31T10:00:00`、`T25:61:61`）怎么办。

| 选项 | 内容                                                                                    |
| ---- | --------------------------------------------------------------------------------------- |
| A    | 要求日期真实存在、时分秒在范围内（时 0–23，分与秒 0–59），否则 `PROPERTY_VALUE_INVALID` |
| B    | 只校验形状                                                                              |

推荐：A。不合法的值写进 frontmatter 后 Obsidian 读不出来；按区间筛选时也会被静默换算成别的日期。
无回复时的默认：A。
影响的文档：[entry.md](entry.md) 第 5.2 节 `datetime` 一行补“必须是真实存在的日期时间”。

### D-27 键盘区块模式的起点与 Tab 顺序

背景：[capture.md 第 6.2 节](capture.md)规定区块模式下 `Tab` / `Shift+Tab` 在“同层单元”间移动，但没有说明模式一打开时的目标是谁（用户没动过鼠标就没有指针位置），也没有说明同层单元怎么排序。

| 选项 | 内容                                                                                                                                   |
| ---- | -------------------------------------------------------------------------------------------------------------------------------------- |
| A    | 起点是键盘焦点所在元素所属的区块，没有焦点时是视口里第一个符合条件的区块；`Tab` 按文档顺序在同一档位的区块间移动，越出窗口时滚动到可见 |
| B    | 起点是视口垂直居中处的区块；顺序同 A                                                                                                   |

推荐：A。键盘用户的“当前位置”就是焦点，可预期。
无回复时的默认：A。
影响的文档：[capture.md](capture.md) 第 6.2 节；[user-stories.md](user-stories.md) 的 US-CAP-14。

### D-28 条目列表的翻页形式

背景：[search.md 第 4 节](search.md)规定每页 50 条、翻页用稳定排序键，没有规定界面形式；列表是日常最高频的页面，也是键盘与读屏用户的主流程。

| 选项 | 内容                                                                     |
| ---- | ------------------------------------------------------------------------ |
| A    | 列表底部“显示更多”按钮，每次追加一页，焦点落在新增的第一行，总数始终显示 |
| B    | 无限滚动                                                                 |
| C    | 页码分页                                                                 |

推荐：A。行为可预期、键盘可达，没有无限滚动对焦点与滚动位置的副作用；追加而不是替换，也保留“回到之前位置”。
无回复时的默认：A。
影响的文档：[extension.md](extension.md) 第 2.3 节；[user-stories.md](user-stories.md) 的 US-LIB-01。

### D-29 同源 iframe 里能不能发起截图

背景：[D-25](#d-25-shadow-root-与同源-iframe-里的选区以及最低浏览器版本) 让页面脚本在所有框架里运行，同源 iframe 里的选区菜单与区块入口因此可用。但截图会话的遮罩、取景坐标和被截取的标签页都属于顶层框架的视口：在子框架里发起截图，要么得到错位的画面，要么直接失败；两个全局快捷键若广播给所有框架，还会在每个同源框架里各开一个会话，按 `Esc` 只结束顶层那一个。

| 选项 | 内容                                                                                                       |
| ---- | ---------------------------------------------------------------------------------------------------------- |
| A    | 子框架里只提供剪藏：选区菜单只有“剪藏”，区块胶囊没有“截图”，区块模式没有 `S`；两个全局快捷键只发给顶层框架 |
| B    | 子框架里的截图转交给顶层框架，按 iframe 在页面里的位置换算取景坐标，截取整个标签页                         |
| C    | 保持原样：入口出现，但在子框架里会失败                                                                     |

推荐：A。入口只出现在能用的地方（与跨源 iframe 里“不出现入口、不报错”同一原则），改动最小；B 要处理嵌套框架的坐标与滚动，价值取决于有多少用户真的在 iframe 里截图。
无回复时的默认：A。
影响的文档：[capture.md](capture.md) 第 2 节表的入口列与第 6.2 节；[extension.md](extension.md) 第 2.1 节与第 7.1 节；[US-CAP-01、US-CAP-14](user-stories.md) 的验收。

**假设**：`H-xx` · 优先级 · 一句话假设 · 通过判据（含分母和阈值）· 验证方式 · 不通过时的动作 · 关联文档。

**新功能规格**（进入真源文件前自检）：

7. 断网时的行为。
