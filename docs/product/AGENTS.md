# 产品文档约定

> 仅适用于 `docs/product/`。这里保存当前产品的行为、契约与验收，不规定最终 monorepo 包结构。
> 更新：2026-10-24。

## 内容边界

- 本目录是产品设计真源：写行为、契约和验收，不写实现位置。不引用代码文件、模块名、消息名或测试数量。
- 从 [README.md](README.md) 的文档地图找到唯一归属文件，再修改对应结论；其他文档用摘要和链接，不复制整套规则。
- 只保留当前的结论和扁平导航，不另建过程性 CHANGELOG；未确认的技术选型不要写成既定工程结构。
- **只写现状，不写演变**：不写“已移出”“取代”“原来”“不再”“旧实现”，不解释缺号，不保留已采纳决策的记录；一个能力不在范围内，就在不做清单里用现在时说明边界，不交代它曾经存在。历史看 git。
- **待确认的决策、风险与开放问题只写进 [validation.md](validation.md)**。其他文件需要引用时，只写条目 ID（如“见 Q-17”）。

## 新功能怎么进来

1. 候选功能是 GitHub issue。产品负责人选定一个开始做时，在 [roadmap.md §3](roadmap.md) 加一行。
2. 一个功能一个 PR：同一个 PR 修改归属的规格文档（契约、页面与文案）、[user-stories.md](user-stories.md) 的故事与验收、[metrics.md](metrics.md) 的指标或事件，以及代码和测试。写规格前用 [validation.md §5](validation.md) 的模板自检。
3. 功能越过 [product.md §2.3](product.md) 的不做清单时，在同一个 PR 里改那一行，写明为哪类核心用户解决什么问题；没有开始做的功能不提前放宽边界。
4. 产品负责人在 PR 评审里确认规格。实现中拿不准、又不必等回复的方案或阈值，登记为 validation.md 的决策（`D-`，带无回复时的默认）或开放问题（`Q-`），先按默认走。
5. 随版本发布后，把能力并入 roadmap.md §2，并删掉 §3 的那一行。

## 状态怎么写

交付状态（发布了什么、正在做什么）只写在 [roadmap.md](roadmap.md)。规格文档与代码在同一个 PR 里修改，描述主分支上的产品，不写“已实现”标记；说某个行为已经发布之前，核对 roadmap.md、源码或测试。

## 编号

| 前缀         | 含义                   |
| ------------ | ---------------------- |
| `US-`        | 用户故事               |
| `M-`         | 指标                   |
| `D-`         | 待确认的决策           |
| `RK-` / `Q-` | 风险 / 开放问题        |
| `AP-`        | 官网的 AI 搜索探针提示 |

编号稳定，不复用，不因排序改变；缺号不需要解释。

## 写作规范

- 使用相对链接；移动文件后检查引用。日期写实际修改日期，图片资源放对应模块的 `assets/`。
- 条目类型的必填字段与预设属性只在 [entry.md](entry.md) 写一次；新增类型或内置属性按它的 §8 清单。
- 示例使用中性来源（如 `engineering.example.com`），不使用真实用户数据；涉及人物时用角色或代号。
- 外部事实（价格、功能、政策）只写在 [market.md](market.md)，带来源链接和核对日期，超过 90 天重新核对。对外页面引用这些事实时同样带日期。
- 设计稿在 [docs/design](../design/README.md)：界面文案和规则先改本目录，再同步设计稿，不在设计稿里另写一套。
